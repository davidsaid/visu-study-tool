# Data format

This page describes every file the app reads and every file a person edits. It is the
contract between the data scripts (`pipeline/`) and the website (`index.html`, `app/`).

The website has no build step. It loads plain JavaScript files with `<script src>`, so it
works when `index.html` is opened from a downloaded folder (`file://`) and on GitHub Pages.
Data files therefore assign to a global instead of being JSON:

```js
window.VISU = window.VISU || {};
VISU.collections = { ... };   // data/collections.js: the list of collections
VISU.bestiary = { ... };      // data/<collection>/bestiary.js
VISU.media = { ... };         // data/<collection>/media.js
VISU.content = { ... };       // data/<collection>/content.js
```

All of them are generated by `python3 pipeline/build.py`. Never edit them by hand.
`app/collection.js` picks the collection (remembered in localStorage as `visu-collection`, or
`?c=<id>` in the address) and loads its three files with `document.write`, which keeps them
classic scripts, in order, before the app.

## `VISU.collections`

```js
{ default: "vertebrados",                     // the collection with the lowest `orden`
  list: [ { id: "vertebrados", name: { es: "Vertebrados", en: "Vertebrates" }, edition: "2026-27",
            species: 308, classes: 9, orders: 99 } ] }
```

## Files people edit

| File | Who edits it | Format |
|------|--------------|--------|
| `collections/<id>/species.csv` | Collection maintainers, once a year | One row per species: `clase, orden, infraorden, nombre_cientifico, nombre_vulgar`. These values are canonical: they are the exam answers. A species in two collections must have the same class, order and infraorder in both |
| `collections/<id>/collection.csv` | Collection maintainers | `key,value` rows: `nombre_es`, `nombre_en` (required), `edicion` (e.g. `2026-27`), `orden` (menu position; the lowest is the default). The folder name is the collection id (`a-z`, `0-9`, `-`) and must never change once published: progress is stored under it |
| `collections/<id>/videos.csv` | Collection maintainers | Optional. `species_id, url, channel, channel_url, title, checked`: one public video per species. `channel` and `channel_url` are required, to credit the author |
| `curation/clades.csv` | Maintainers | The clade backbone shared by every collection: `node_id, parent_id, scientific, name_es, name_en, source_url`. The prefix of `node_id` says what a row is: `deep:` (path from Life towards the root clades), `clade:` (backbone), `class:` / `order:` / `infraorder:` (attaches a group of the lists to its parent and names it), `grade:` (a class of the lists that is not a clade, such as Reptilia). A collection's tree keeps only the rows above its own classes. See `pipeline/README.md` |
| `curation/synonyms.csv` | Maintainers | `binomial, synonym, verdict (same_taxon/parent_of_split), note`: overrides the rule that decides whether a dataset row found under another name may be used |
| `curation/corrections.csv` | Maintainers | Notes where a list's value differs from a current authority, or from what another course writes: `species_id, field, bestiary_value, suggested_value, confidence (certain/suggested/contested/course), source_url, note_es, note_en, status (pending/accepted/rejected), collection`. `bestiary_value` is the list's value (the answer the tool accepts); `field` is a `species.csv` column (`nombre_cientifico`, `orden`, `nombre_vulgar`). A `course` row says the course of `collection` (a collection id, required for these rows) writes `suggested_value`; the card names that course and says the tool accepts `bestiary_value`, instead of "write what the bestiary says". Only `accepted` rows are shown on cards |
| `curation/media_overrides.csv` | Collection maintainers | `species_id, action (pin/exclude/crop), media_id_or_url, value`. Survives yearly re-runs |
| `content/species/<species_id>.json` | Authors (LLM draft, then a person) | Field marks, look-alikes, dimorphism, etymology. See below |
| `content/groups/<node_id>.json` | Authors | Summary, diagnostic traits, "do not confuse with". See below |

Every CSV is read by `pipeline/common.py` `read_csv`: separator `,` or `;` (taken from the header
line; Excel in a Spanish locale saves `;`), encoding UTF-8 with or without a BOM. Any other
encoding stops the build with a message asking for "CSV UTF-8". Every row must have exactly as
many fields as the header, and header names must be unique; a value that contains the separator
goes in double quotes. Every link (video `url` and `channel_url`, `source_url`, content
`sources[].url`, photo `license_url` and `source_url`) must start with `http://` or `https://`; the build stops on
anything else, and the app also refuses to make a link from any other scheme. The build writes
all its outputs to temporary files and renames them only when every step has succeeded.

## Identifiers

- **Species id:** the binomial in lower case with an underscore, `lynx_pardinus`. Issued
  when a species first appears and never reused.
- **Node id:** `class:Aves`, `order:Accipitriformes`, `infraorder:Cetacea`, or a clade slug
  from `clades.csv` such as `clade:archosauria`. A species id is also a node id (leaves).
- **Collection id:** the folder name under `collections/`, such as `vertebrados`.
- **Learner progress** (localStorage and exported `.json` copies; shape in `app/store.js`): one
  localStorage key per collection, `visu-progress-v1` for `vertebrados` (the key from before there
  were collections) and `visu-progress-v1:<id>` for the others. An exported copy carries its
  `collection` (copies without one belong to `vertebrados`) and is only accepted by that collection.
  `normalizeProgress` in `app/engine.js` keeps only known keys with the expected types, coerces
  numbers in strings and ISO dates, cuts typed answers to 80 characters and drops anything else.
  It runs on every load from localStorage. An imported file in which any value fails that check
  is refused as a whole, with a message, and the current progress is left untouched.
- **Card id** (in the learner's progress): `<species_id>:<skill>`, where skill is one of
  `class, order, genus, species, common`.

## `VISU.bestiary`

```js
{
  collection: { id: "vertebrados", name: { es, en } }, edition: "2026-27", generated: "2026-11-01",
  species: {
    "lynx_pardinus": {
      id, binomial: "Lynx pardinus", genus: "Lynx", epithet: "pardinus",
      class: "Mammalia", order: "Carnivora", infraorder: null,   // the list's values (the answers)
      common_es: "Lince ibérico",                                // the list's value
      common_en: "Iberian lynx",                                 // from Wikidata, may be null
      family: "Felidae", authority: "(Temminck, 1827)",          // may be null
      keys: { gbif: 2435261, wikidata: "Q129727", inat: 41975 },
      video: { url, channel, channel_url, title,                 // from videos.csv; null if none
               status: "ok" | "link_only" | "broken" | "unchecked",   // link_only: plays on YouTube only
               checked: "2026-11-01" },                         // unchecked: not in links.json yet (checked = videos.csv date)
      facts: [ Fact, ... ],
      corrections: [ Correction, ... ]                           // accepted only
    }
  },
  tree: {
    root: "clade:vertebrata",        // the top clade above the collection's classes; a deep: row when
                                     // they span several top clades; "clade:collection" when none is in clades.csv
    deep_path: [ { scientific, es, en, source_url } ],           // Life → … → the root
    nodes: {
      "order:Carnivora": { id, parent, children: [...], rank: "clade|class|order|infraorder|species",
                           scientific, name: { es, en }, teacher_rank: "class|order|infraorder|null",  // rank in the list
                           grade: "Reptilia" | null, species_count,
                           source_url }                    // Wikipedia link for clades and the list's groups; null for species
    }
  },
  sources: { "<source_id>": { title, url, license, retrieved } },
  corrections: [ Correction, ... ]                               // all accepted for this collection
}
```

### Fact

```js
{ field: "distribution|habitat|diet|mass|length|dimorphism|sex_determination|lifespan|
          reproduction|activity|migration|iucn|spain",
  es: "Cabeza-cuerpo ♂ 75–88 cm", en: "Head–body ♂ 75–88 cm",   // display text, both languages
  src: ["amniote_lhd"],                                          // keys into sources
  match: "exact" | "synonym" | "rule",                           // how the record was matched
  note: null }                                                    // or { es, en }, e.g. "rule: mammals are XY"
```

A fact without at least one `src` must not be written. Values from a synonym match that is a
split species mapped to its old parent are dropped, not shown.

### Correction

```js
{ species_id, field, bestiary_value, suggested_value, confidence, source_url, note: { es, en } }
// species_id is null for notes about the whole list (e.g. a typo in the PDF header)
```

## `VISU.media`

```js
{ "lynx_pardinus": [ { id: "inat-187857126", file: "media/lynx_pardinus/3f9a1c.jpg",
    w: 1024, h: 768, author: "Nils", license: "CC BY 4.0", license_url, source: "inaturalist|commons",
    source_url, modified: "resized", crop: null } ] }
```

File names are opaque, so they never reveal the answer. `crop` is `[x, y, w, h]` as fractions
of the photo or `null`. Without a crop, the app never crops the photo.

`pipeline/media.py` produces this file (`select` → `fetch` → `emit` → `report`). Its
intermediate, `curation/media_manifest.json`, holds one record per photo with the fields above
plus provenance (`author_url`, `page_url`, `original_url`, `retrieved`, `role`, `orig_w`,
`orig_h`, `selection`). `license` is one of `CC0 1.0`, `CC BY <version>`, `CC BY-SA <version>`, `CC BY-NC <version>`, `CC BY-NC-SA <version>` (never ND)
or `Public domain` (Commons only). Every photo is listed in the generated `media/CREDITS.md`.

## `VISU.content`

```js
{ species: { "lynx_pardinus": {
    field_marks: { es: [..], en: [..], parts: [["shape", "wings"], ..] },
    lookalikes: [ { binomial, es, en } ],
    dimorphism: { es, en }, etymology: { es, en }, trivia: { es: [..], en: [..] },
    sources: [ { title, url, license, retrieved } ],
    status: "draft" | "checked" } },
  groups: { "order:Accipitriformes": {
    summary: { es, en }, traits: { es: [..], en: [..] }, contrast: { es, en },
    etymology: { es, en }, sources: [...], status } } }
```

`content/species/<id>.json` and `content/groups/<node_id>.json` contain exactly one of
these objects. In group file names the colon becomes `__`: `order__Accipitriformes.json`.

`field_marks.parts` (optional) has one entry per field mark: the body parts it describes, 1 to 3 of
`shape`, `head`, `colour`, `skin`, `wings`, `fins`, `legs`, `tail`, `sexes`, `young`, `behaviour`, most
important first. After a wrong species, the mistake screen uses them to line the two cards' marks up
part by part. They add no facts, so they need no source. The build stops if the counts don't match or
a label is unknown.

`etymology` is "what the name says": for a species, the meaning of the genus and the epithet;
for a group, the roots of its name. The app shows it as a memory aid on the cards (class, order
and scientific name together on the species card) and after a wrong answer, for the box that was
missed. A class of the list that is not a tree node (the grade Reptilia) still gets its group
file, `class__Reptilia.json`, so its etymology can be shown.
